# 需求分析提示词

## 上下文

你正在为一个已有应用分析一条软件需求。

输入：

- 需求：`{{requirement}}`
- 产品背景：`{{product_context}}`
- 现有架构：`{{architecture}}`
- 相关文件：`{{relevant_files}}`

## 约束

- 不要臆造 API、数据库字段或业务规则。
- 明确区分事实与假设。
- 识别信息缺口，而不是悄悄填补它。
- 除非有充分理由，否则保持现有架构不变。

## 指令

分析该需求，并产出一份可直接进入实现的规格说明。

## 结果

返回：

1. 目标
2. 用户流程
3. 功能性需求
4. 非功能性需求
5. 可复用的现有组件 / 服务
6. 可能改动的文件
7. API / 数据层面的影响
8. 边界情况
9. 待确认问题
10. 验收标准

## 验证

定稿之前：

- 每条需求都至少映射到一条验收标准
- 假设被显式标注
- 没有任何臆造的 API 契约被当作事实陈述
- 边界情况在适用时覆盖加载中、空、错误和权限状态
