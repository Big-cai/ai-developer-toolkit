# AI 开发方法论

## 1. 理念

AI 辅助软件工程应被当作一个受控的工程闭环，而不是一次聊天。

```text
需求
    ↓
上下文
    ↓
约束
    ↓
计划
    ↓
执行
    ↓
验证
    ↓
人工复核
    ↓
反馈
    ↺
```

核心规则是：

> 输出后果越重大，验证边界就应该越强。

## 2. C-C-C-R-V 框架

### 上下文（Context）

把模型需要的信息给它：

- 业务背景
- 仓库结构
- 相关源文件
- API 契约
- 数据模型
- 现有约定
- 设计系统
- 运行时约束

### 约束（Constraint）

显式划定边界：

- 允许使用的技术
- 禁止使用的技术
- 可以 / 不可以改动的文件
- 兼容性要求
- 安全要求
- 性能要求
- 编码规范

### 指令（Command）

定义一个具体的目标。

差的写法：

> 优化一下这个项目。

好的写法：

> 在不改变 API 响应契约的前提下，为现有用户表格增加分页。

### 结果（Result）

明确期望产出的东西：

- 实施方案
- 变更文件
- 代码
- 测试
- 迁移脚本
- 评审报告

尽可能使用结构化 schema。

### 验证（Validation）

独立地检查结果：

- 需求检查清单
- 类型检查
- lint
- 单元 / 集成测试
- 构建
- 静态分析
- 安全检查
- 人工复核

## 3. 上下文工程

上下文是有意识地管理的，而不是把整个仓库一股脑塞给模型。

一个有用的上下文分层：

```text
L0：任务
L1：业务需求
L2：架构 / 项目规则
L3：相关代码
L4：接口 / schema
L5：示例
L6：验证标准
```

只放入能够改变决策的上下文。

## 4. 任务分解

当出现以下情况时，一个大的请求应当被分解：

- 子任务目标不同
- 子任务需要不同的上下文
- 子任务可以被独立验证
- 并行执行有价值
- 故障隔离很重要

不要仅仅为了让架构看起来更高级而分解。

## 5. 人在回路中的边界

AI 可以提出或实现变更，但工作流为以下事项定义了明确的人工检查点：

- 有实质影响的架构决策
- 安全敏感的变更
- 数据库迁移
- 破坏性操作
- 对外可见的行为
- 最终的合并 / 发布决策

## 6. 失败分类

当 AI 的输出失败时，先给失败归因，再改提示词：

| 失败类型 | 典型原因 | 干预手段 |
|---|---|---|
| 需求理解错误 | 上下文不足 | 改进「上下文」 |
| 违反项目规则 | 约束太弱 | 改进「约束」 |
| 实现方式错误 | 任务描述含糊 | 改进「指令」 |
| 格式错误 | 输出契约未明说 | 定义「结果」schema |
| 看着对却跑不通 | 缺少验证 | 强化「验证」 |
| 重复旧错误 | 没有反馈闭环 | 记录失败模式 |

## 7. 质量闭环

```text
提示词 / 技能
   ↓
运行
   ↓
评估
   ↓
给失败归因
   ↓
只改一个变量
   ↓
再次运行
   ↓
对比
```

目标不是写出最长的提示词。目标是构建最小的、可靠的指令系统，从而稳定产出可接受的结果。
